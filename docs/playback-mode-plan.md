# 顺序播放与随机播放切换方案

记录日期：2026-11-10（Asia/Shanghai）；来源设备：Ubuntu 开发电脑。

状态：2026-11-10 已实施播放顺序模块、真实总数与内容版本透传、统一切歌入口、播放模式菜单和 NVS 保存；主机测试、受限堆 UI 预览和 ESP-IDF 5.5.4 构建通过，已烧录实机。QQ 随机跨页切歌成功，用户确认本轮操作测试无问题；整轮不重复、上一首、长时间稳定性等完整验收尚未完成。按用户反馈将播放模式移到长按 OK 导航首项并默认选中。以下保留方案及验收标准。

## 目标与现有基础

在 Folo Music 中提供顺序播放和随机播放切换，保持设备端直连网易云，不增加服务器，不更换音频解码方案。

评估基线为当前 2.1.1 源码：

- `firmware/ai-passport/main/netease_app.c` 已有页内切歌、跨页加载、歌曲结束后自动切歌，以及独立的浏览与播放上下文。顺序播放到歌单末尾后停止。
- `firmware/ai-passport/main/netease_app_logic.c` 负责三键操作和菜单状态；手动切歌、自动切歌及不可播放歌曲的后续选择目前分散在不同入口。
- 歌曲详情每页最多 8 首。随机范围必须覆盖整个当前播放歌单，不能仅打乱当前缓存页。
- `firmware/components/netease_direct_client/direct_http.c` 支持按 offset 获取歌曲，内部统计总数，保留最多 512 个歌曲 ID 的窗口缓存；当前歌曲分页结果未向上暴露完整总数。

结论：现有架构可支持，预计为中等规模改动。主要工作是统一播放顺序管理、补充菜单和状态保存，风险集中在运行内存、随机跨页请求耗时及异常一致性。

## 建议交互与行为

长按 OK 打开导航，第一项为「播放模式」并默认选中，短按 OK 即可进入选择「顺序播放 / 随机播放」；其余项依次为返回播放、当前歌曲列表、我的歌单、音量、设置。播放页显示当前模式。沿用三键操作，不增加组合键或双击。

| 行为 | 顺序播放 | 随机播放 |
| --- | --- | --- |
| 自动切歌或按下一首 | 歌单原始顺序的下一首 | 打乱队列中的下一首 |
| 按上一首 | 歌单原始顺序的上一首 | 返回随机队列中的上一首；随后按下一首沿原队列前进 |
| 手动在列表点歌 | 播放选中歌曲，之后按原始顺序继续 | 先播放选中歌曲，再以它为起点重建本轮随机队列 |
| 切换模式 | 当前歌曲与暂停状态不变，从下一次切歌起采用新模式 | 同左；当前歌曲计入本轮已播放项 |
| 到达末尾 | 保留现有行为，停止并显示结束页 | 一轮内不重复，整轮完成后重新打乱；多首时避免新一轮首曲与上一轮末曲相同 |

默认顺序播放。模式设置保存到 NVS，重启后保留；随机队列仅在 RAM 中维护，不持久化播放进度。歌曲列表保持原始排列，播放页曲序仍表示歌曲在原歌单中的位置。

## 实现方案与边界

1. 增加独立、可进行主机测试的播放顺序模块，维护播放模式、歌单标识、总曲数、随机序号队列与游标。手动上一首、下一首、自动结束和不可播放后的跳过使用同一套目标选择逻辑。
2. 顺序模式按原始索引推进；随机模式对歌曲序号进行 Fisher–Yates 洗牌，抽样需避免取模偏差。保存随机队列后，通过游标支持前后切歌；重复歌曲 ID 是否视为同一首需在实施时结合真实歌单数据明确，本方案默认以歌单条目为单位。
3. 将底层已统计的歌单总数传递给上层，不只依赖歌单列表中的数量快照。先确定目标绝对索引，再计算对应分页和页内索引，复用当前歌曲详情、播放 URL、封面、歌词和音频启动链路。
4. 浏览其他歌单不改变正在播放的队列。只有实际开始播放另一个歌单、手动点歌重建本轮、账号切换或检测到当前歌单内容变化时，才重建或清理相关队列；过期请求结果不能覆盖新播放上下文。
5. 模式切换不停止当前音频、不重新请求当前歌曲；NVS 保存由工作任务执行，不在按键回调中阻塞。保存失败需明确反馈，不将未保存状态显示为已持久化。
6. 无版权或无资源保留可见提示，由用户触发跳过时遵循当前模式；网络错误沿用明确的失败和重试流程，不默认为歌曲不可播。若后续采用自动跳过，应限制一轮尝试次数，全部不可播时停止并提示，不能无限循环。

## 内存与性能约束

- 只新增序号队列，不加载全歌单的歌曲详情、封面或歌词。32 位序号的 1,000 项队列约为 4,000 字节，仅为计算值，不是实测内存增量，还需计入分配器和其他状态开销。
- ESP32-C3 无 PSRAM。分配前检查数量、乘法溢出和预算；可支持的歌单上限需根据音频、TLS、封面、歌词共存时的空闲堆与最大连续块确定，不能只依据 Flash 余量判断。
- 队列分配失败时保持原有效模式和播放状态并提示失败，不静默改成当前页随机或宣称全歌单随机。
- 随机跳到 ID 缓存窗口外，可能重新请求并流式解析歌单详情，因此大歌单随机切歌可能慢于相邻顺序切歌。首版复用有界缓存，不直接扩大为全歌单 ID 常驻缓存。
- 保留现有音频活动期间停止推测性预取、播放前释放闲置 API TLS 等稳定性措施。记录缓存命中、切歌耗时、空闲堆和最大连续块，不预先承诺切歌秒数。
- 歌单发生变化或目标页为空时，刷新总数及必要元数据后重建队列；仍无法定位则明确提示，不能把失效索引当作播放成功。相同数量下的内容变化也不能仅靠总数识别，具体刷新与失效策略在实施时确定。

## 后续实施与验收

实施顺序：播放顺序模块与主机测试 → 总数及任意目标页加载 → 合并各切歌入口 → 菜单、模式显示与持久化 → 构建和实机验收。

验收至少覆盖：

- 空歌单、单首、两首、跨 8 首分页、超出 512 个 ID 缓存窗口的大歌单。
- 整轮无重复、轮次边界不立即重复、上一首回退与下一首重走原队列。
- 顺序播放到末尾停止、随机轮次续播、手动点歌与播放中切换模式，暂停时切换仍保持暂停。
- 浏览其他歌单时后台切歌、切换播放歌单、账号切换、歌单内容变化及过期请求结果。
- 无版权、无资源、网络失败与重试、队列分配失败、设置保存失败及重启恢复模式。
- 主机逻辑测试、项目要求的相关静态检查与固件构建；实机检查菜单显示、三键操作、音频连续性、切歌耗时及堆内存。

实施说明：模块为事务式 peek/commit，网络失败不消费目标；用户确认跳过无资源条目后才推进。随机模式保留当前轮、上一轮和待提交新轮，序号数组实际为每条目 12 字节，1,000 条目约 12,000 字节，不是原单队列的 4,000 字节；重建时还需旧队列与候选队列短暂共存。设备空闲时队列预算上限 16 KiB、预留 16 KiB；音频活动时已分配音频资源，不再重复预留同一份预算，改为预留 8 KiB、队列上限 4 KiB。两种状态都检查实时剩余堆和最大连续块，超限明确失败，不缩短歌单；实际支持上限及长时间音频/TLS共存仍需实测确认。切歌先停旧音频，再读取目标页，避免两条 TLS 争用内存；模式切换不停止当前歌曲。随机回退最多保留到上一轮开头。

主机逻辑覆盖空/单/两首、9 首与 1,025 首、整轮无重复、轮界避免连续重复、回退及重走、无偏抽样、失败保持状态。直连协议测试覆盖完整 ID 顺序指纹、512 窗口外同数量变化、TTL、空页/空歌单；UI日夜模式、保存失败提示和暂停页面完成8次受限堆预览。实机菜单、音频连续性、NVS失败注入、重启恢复、真实大歌单耗时及堆余量尚未验证，不把上述自动验证作为设备验收通过。
